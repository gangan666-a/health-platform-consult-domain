## 1. 项目背景

M1 已交付「浏览商品 → 下单 → 模拟支付 → AI 智能导购」闭环（四个微服务：`product-service` :8081、`order-service` :8082 为 BFF、`payment-service` :8083、`recommend-service` :8084）。本期 M2 的核心诉求是打通**医药电商**合规交易主链路：用户购买处方药（Rx）时，必须先与在线医生进行**实时文字问诊**，医生根据病情**开具处方**，用户**凭有效处方才能下单支付**。

合规要点（产品语义）：处方药（Rx）不可无处方直接购买；**一张有效处方只能消费一次**（防复用）；处方有有效期；问诊会话有明确的开始/结束判定。本期为演示环境：在线医生为**固定演示医生身份**（`demo-doctor`），不做真实医师资质审核，仅演示完整的产品流程与边界判定。

系统现状要点（摘自代码，作为集成点基线）：

- **商品模型**：`Product.java` / `ProductDTO.java` 含 `id/name/description/price/stock/imageUrl/category/createdAt`，**无处方药（Rx）属性**；品类由 `category` 字段表达（M1 种子数据 31 商品、15 品类，按商品名 upsert）。
- **下单流程**：`OrderService.createOrder(productId, quantity, receiverName, receiverPhone, receiverAddress)` → 校验数量/价格/库存 → 商品服务**原子扣减库存** → 本地生成订单 + 明细快照；本地保存失败时补偿回补库存。`OrderForm.java` 为下单表单（productId/quantity/收货三项），**无处方号字段**。
- **BFF 职责**：`order-service` 承载全部页面（`ShopController`），商品数据经 `ProductClient` 代理 `product-service`；浏览器唯一入口 `http://localhost:8082`。
- **页面路由**：`/product/{id}` 商品详情 → `/order/confirm` 确认订单 → `/order` 提交订单 → `/order/{orderNo}` 订单详情 → `/order/{orderNo}/pay` 支付 → `/order/{orderNo}/pay/success` 支付成功。
- **技术栈**：Spring Boot 3.5 / Spring Data JPA / MySQL 8.4 / 每服务独立 schema；本 M2 新增 `consult-service` 使用 **Netty WebSocket** 承载 IM 实时通信。

## 3. 项目目标

1. **G1 · 药品品类与 Rx 标记**：商品体系新增「药品」品类；药品商品携带「是否处方药（Rx）」属性；OTC 可普通购买，Rx 必须凭有效处方才能下单。
2. **G2 · IM 在线问诊**：用户可从 Rx 药品详情页发起实时文字问诊，与在线医生进行 WebSocket/Netty 实时聊天；消息持久化、历史可查。
3. **G3 · 处方开具**：医生基于会话开具处方（药品 + 用法用量 + 有效期）；处方与发起会话的药品绑定、与用户绑定，不可跨会话/跨人使用。
4. **G4 · 处方购药（防复用）**：凭有效处方下单；**一张处方只能被一个订单消费一次**（并发下也保证），处方有有效期；下单时服务端原子校验处方有效性与匹配性，校验通过才允许下单支付。
5. **G5 · 会话生命周期可判定**：会话状态（等待接入/进行中/已结束）明确；主动结束、断线、超时、开方完成四种结束判定规则清晰、确定、可测，不误判。

## 6. 名词与术语

| 术语 | 说明 |
| --- | --- |
| 药品 / OTC / Rx | 药品为新增品类（`category=药品`）；**OTC** 为非处方药，可普通购买；**Rx** 为处方药，必须凭有效处方下单 |
| Rx 标记 | 商品上的「是否处方药」布尔属性（本文档字段名 `rxFlag`，`true`=处方药 Rx） |
| 问诊会话（Session） | 用户就某一 Rx 药品发起的在线问诊，含消息流与医生；状态 `WAITING 等待接入 / ONGOING 进行中 / ENDED 已结束` |
| 医生接入 | 医生点击「接诊」，将会话从 `WAITING` 置为 `ONGOING` 的动作 |
| 处方（Prescription） | 医生在本会话内开具的用药凭证；含药品 + 用法用量 + 有效期；状态 `ACTIVE / USED / EXPIRED / REVOKED` |
| 处方消费（Consume） | 下单时对处方做「校验 + 一次性置为 USED」的**原子**操作，服务端唯一边界 |
| 可下单窗口 | 处方开具时刻起至 `validUntil`（默认 7 天）内可凭该处方下单的时段；与会话是否结束无关 |
| 断线缓冲 | 连接断开后允许重连的宽限期（60s），期内重连会话继续、消息不丢 |
| 空闲超时 | 会话进行中双方连续无消息的时限（30min），超时自动结束 |
| seq（消息序号） | 会话内单调递增的消息序号，保证同会话双端并发发送时接收顺序一致 |
| 演示身份 | 浏览器首次访问生成 `userId`（localStorage/cookie 保存），医生为固定 `demo-doctor`；用于会话隔离（见第 7 节） |

## 7. 用户角色与权限（含隔离）

| 角色 | 可访问能力 | 权限边界 / 隔离 |
| --- | --- | --- |
| **买家（患者）** | 浏览药品、看 Rx 标记、发起问诊、在**自己的**会话内聊天、收取**自己的**处方、凭处方下单支付、查看「我的问诊」与「我的处方」 | **只能查看/加入自己的会话与处方**（服务端按 `userId` 强制校验）；不可进入他人会话；不可直接购买 Rx 无处方 |
| **在线医生（`demo-doctor`）** | 查看「待接诊」列表、接入会话、在**被分配/自己接入**的会话内聊天、对本会话开具处方、撤销未使用处方 | **只能操作自己被分配/接入的会话**（服务端按 `session.doctorId` 校验）；医生开具的处方只能绑定本会话药品，不能跨会话开方 |
| 运营 / 管理员 | 查看种子药品数据与 Rx 标记 | 本期无管理后台（NG-12） |
| 研发 / 测试 | 执行验收标准、模拟异常 | 可模拟医生离线、断线、并发下单、伪造处方号 |

**隔离实现约定（产品要求，落实到服务端最终校验）：**

- 浏览器首次访问时生成 `userId`（UUID）并持久化（localStorage / Cookie）；后续所有问诊相关 REST 请求与 WebSocket 建连均携带 `userId`；服务端对「查询会话/发消息/查处方」校验 `session.userId` / `prescription.userId` 与请求方一致，不一致一律拒绝（返回「无权访问该会话/处方」）。
- 医生操作一律要求 `doctorId=demo-doctor` 且与 `session.doctorId` 一致；医生对非本会话开方被拒绝。
- 页面隐藏入口只是体验，**隔离的正确性由服务端强制校验**（与 M1「服务端最终校验」原则一致）。

## 8. 功能需求（Functional Requirements）

> 编号规则：FR-D1 药品、FR-C1~C4 问诊、FR-P1~P3 处方；AC 编号见第 12 节（AC-xxx-y）。每条的「现状差异」标注相对 M1 代码的改动点。

### FR-D1 药品品类与 Rx 标记

**需求描述**：商品体系新增「药品」品类；药品商品带「是否处方药（Rx）」属性（`rxFlag`）。列表页与详情页明确区分 OTC / Rx；**Rx 药品禁止无处方直接购买**，入口改为「在线问诊购药」。

- 药品在列表页参与正常展示（含品类筛选语义），详情页展示 Rx 徽标。
- **OTC** 药品：展示「OTC · 非处方药」，可普通购买（沿用「立即购买」）。
- **Rx** 药品：展示「Rx · 处方药」+ 明确文案「需在线问诊开具处方后方可购买」；详情页**不提供**「立即购买」直达下单入口，改为「在线问诊购药」按钮（进入 FR-C1）；即使绕过前端直达确认订单/下单接口，服务端也必须拒绝（见 FR-P2 / EX-IM-1）。
- 药品种子数据至少含：**多个 OTC**（如 布洛芬缓释胶囊、维生素C 泡腾片、健胃消食片、氯雷他定片、板蓝根颗粒）与**多个 Rx**（如 阿莫西林胶囊、硝苯地平缓释片「降压药」、复方氨酚烷胺片「复方感冒药」、头孢克肟分散片）。种子数据按商品名 upsert（沿用 M1 方式），老库药品缺失 Rx 标记时回填默认 `false`。

**前置条件**：`product-service` 可用；`product` 表增加 `rx_flag` 字段（`ddl-auto=update` 自动建列）；种子数据含药品品类条目。

**主流程步骤**：
1. 用户访问首页/列表页，`order-service` 代理 `GET /api/products` 获取全量商品（含 `rxFlag`），药品商品带品类「药品」。
2. 进入 `/product/{id}` 详情页：
   - `rxFlag=false`（OTC）：展示「OTC · 非处方药」，提供「立即购买」。
   - `rxFlag=true`（Rx）：展示「Rx · 处方药」+「需在线问诊开具处方后方可购买」，「立即购买」替换为「在线问诊购药」。
3. 用户点击「在线问诊购药」→ 进入 FR-C1。

**后置条件**：OTC 可正常下单；Rx 详情页无直达下单入口；Rx 直达下单在服务端被拒绝。

**现状差异**：M1 `Product.java` / `ProductDTO.java` 无 `rxFlag` 字段，需新增；`ShopController.confirmOrder` 需在 `quantity>stock` 校验前增加 Rx 拦截逻辑（Rx 且无处方 → 抛「处方药需先在线问诊开具处方」）。

### FR-C1 创建问诊会话

**需求描述**：用户从 Rx 药品详情页进入问诊：创建（或复用）针对该药品的问诊会话，进入聊天页。会话开始于创建成功、状态 `WAITING`（等待医生接入）。

- 会话必须绑定**发起用户**与**目标药品**（`session.userId`、`session.productId`）。
- **复用规则**：若该用户对同一药品存在「未结束」会话（`WAITING` 或 `ONGOING`），再次点击问诊时**复用**该会话并跳转；否则新建会话。
- 创建成功后跳转聊天页 `/consult/{sessionNo}`（FR-C2）。
- 「我的问诊」入口展示该用户全部会话及状态（FR-C3）。

**前置条件**：`consult-service` 可用；用户已从 Rx 药品详情页进入。

**主流程步骤**：
1. 用户点击 Rx 详情页「在线问诊购药」。
2. `order-service`（BFF）代理 `consult-service POST /api/sessions {userId, productId}`。
3. `consult-service`：校验商品存在且 `rxFlag=true`（非 Rx 药品拒绝建会话）；查询该用户对该药品的未结束会话——存在则直接返回（复用）；否则创建 `WAITING` 会话并返回 `sessionNo`。
4. 跳转聊天页，页面先 REST 拉取历史消息（新会话为空），再建立 WebSocket 连接。

**后置条件**：会话创建成功（`WAITING`）或复用成功；聊天页可收发消息。

**现状差异**：全新能力，现状无。

### FR-C2 IM 实时聊天

**需求描述**：用户与医生在会话内进行**实时文字**聊天（WebSocket/Netty），支持双向收发、消息持久化、历史可查。

- 消息模型：`senderType(USER/DOCTOR/SYSTEM)`、`senderId`、`content`、`seq`（会话内单调递增）、`createdAt`。
- **实时性**：WebSocket 长连接双向推送；服务端收到消息**先持久化（落库成功）再向会话内转发/确认**，保证消息不丢（NFR-6）。
- **顺序性**：会话内 `seq` 单调递增，服务端按会话串行落库与转发，双端同时发送也不乱序（NFR-3）。
- **历史可查**：进入会话页先 `GET /api/sessions/{sessionNo}/messages` 拉取历史（按 seq 升序），再增量接收实时消息；断线重连后按「本地最大 seq + 1」增量补拉（NFR-6）。
- 系统消息：医生接入、会话结束、处方开具等关键事件以 `SYSTEM` 消息落库并推送（如「医生已接入会话」「医生已开具处方 RXxxx，有效期至 XXXX」）。
- 演示环境**仅纯文字**，不做已读回执/图片/语音（NG-5 / NG-6）。

**前置条件**：会话存在且用户有权限（`userId` 匹配）；`consult-service` WebSocket 端点可用。

**主流程步骤**：
1. 用户进入聊天页，建立 WebSocket 连接（携带 `sessionNo` 与 `userId`）。
2. 用户发消息：`content` 非空（≤ 500 字）→ 服务端按会话串行分配 `seq` → 落库 → 推送至会话内在线端（用户本人端回显 + 医生端）。
3. 医生接入后发消息：同上，推送至用户端与医生端。
4. 发送失败/断线期间的消息：发送端标记未送达，重连后由「历史增量补拉」补齐，不产生消息缺失。

**后置条件**：消息按发送顺序被双方收到；落库消息在历史中可查；断线重连后消息不丢。

**现状差异**：全新能力，现状无（M1 无任何即时通信）。

### FR-C3 会话管理

**需求描述**：会话状态为 `WAITING（等待医生接入）/ ONGOING（进行中）/ ENDED（已结束）`。用户可查看「我的问诊」（含状态）、可**主动结束**会话；医生可**接入**会话、可**主动结束**会话；结束判定规则见 FR-C4。

- 状态流转（合法）：
  ```
  创建 ─▶ WAITING ──医生接入──▶ ONGOING ──结束判定──▶ ENDED（终态）
  WAITING / ONGOING ──用户或医生主动结束──▶ ENDED
  ```
- `WAITING`：用户已创建会话，医生未接入；用户可发消息（进入「等待医生回复」语义）、可主动结束。
- `ONGOING`：医生已接入，双方可聊天；双方均可主动结束。
- `ENDED`：终态；**只读**（可查看历史消息），**禁止**再发消息、禁止再开方（见 FR-C4 / EX-IM-17 / EX-IM-18）。
- 「我的问诊」列表按创建时间倒序展示该用户全部会话，含目标药品、状态、最近消息时间。
- 医生端「待接诊」列表展示 `WAITING` 会话，医生点击「接诊」进入 `ONGOING`。

**前置条件**：会话存在；操作者身份合法（用户= `session.userId`，医生= `session.doctorId`）。

**主流程步骤**：
1. 用户访问「我的问诊」→ 列表展示自己的会话与状态；`WAITING/ONGOING` 会话可进入聊天页，`ENDED` 会话可查看历史。
2. 用户点击「结束会话」（`WAITING/ONGOING`）→ 会话置 `ENDED`（`endReason=USER_ENDED`），推送系统消息，关闭双方连接。
3. 医生在待接诊列表点击「接诊」→ `WAITING → ONGOING`，推送系统消息「医生已接入」。
4. 医生点击「结束会话」（`ONGOING`）→ 置 `ENDED`（`endReason=DOCTOR_ENDED`）。

**后置条件**：状态机合法；结束后的会话只读；「我的问诊」状态正确。

**现状差异**：全新能力，现状无。

### FR-C4 会话结束判定（产品规则）

> 本条为「会话如何结束」的**核心判定规则**，必须确定、可测、不误判。以下常量为本期演示默认值，均可在 `consult-service` 配置。

| 结束方式 | 触发条件（判定规则） | 结束原因 `endReason` | 判定要点（可测） |
| --- | --- | --- | --- |
| **主动结束（用户）** | 用户点击「结束会话」（`WAITING` 或 `ONGOING`） | `USER_ENDED` | 立即置 `ENDED`；系统消息；双方连接关闭 |
| **主动结束（医生）** | 医生点击「结束会话」（仅 `ONGOING`） | `DOCTOR_ENDED` | 立即置 `ENDED`；系统消息 |
| **断线超时** | 任一端连接断开（心跳 30s 未收到 / 连接关闭）后，**60s 内未重连** | `DISCONNECT_TIMEOUT` | 60s 内重连成功 → 会话**继续**、不结束、消息按 seq 补齐；超 60s 未重连 → 置 `ENDED` |
| **空闲超时** | `ONGOING` 会话双方连续 **30 分钟**无任何文本消息（心跳不计入活动） | `IDLE_TIMEOUT` | 置 `ENDED`；系统消息 |
| **开方完成** | 医生成功开具处方（FR-P1） | `PRESCRIPTION_ISSUED` | 会话**自动结束**（终态）；「可下单窗口」由**处方有效期**（默认 7 天）决定，**与会话结束无关**——会话结束后用户仍可在处方有效期内凭处方下单 |

**归属与可下单窗口的明确界定：**

- 医生开具处方成功后，**本次问诊诊疗完成**，会话自动置 `ENDED`（`PRESCRIPTION_ISSUED`），推送系统消息「医生已开具处方 RXxxx，有效期至 XXXX」。
- **可下单窗口** = 处方 `validUntil`（默认开具后 7 天）。窗口内用户可随时凭处方下单（FR-P2），即使会话已结束；窗口结束后处方置 `EXPIRED`，不可下单。
- 处方开具后若用户有**追问需求**，需新建会话（新会话与旧处方独立）。

**不结束（防误判）的明确约定：**

- 会话处于 `WAITING`（医生未接入）且双方连接正常：**不因「医生未接入」自动结束**（医生忙碌场景，见 EX-IM-10 / EX-IM-16）。
- 会话内一方短暂断线且在 60s 缓冲期内重连：**不结束**。
- 会话进行中双方有任意文本消息（含医生正在输入）刷新活动时间：**不触发空闲超时**。
- 空闲超时计时**仅从 `ONGOING` 开始**，`WAITING` 阶段不计时。

**并发结束判定的一致性：** 会话状态变更在服务端**按会话加锁串行化**；「结束」与「发消息/开方」同时到达时，以先提交者为准——会话一旦提交为 `ENDED`，之后到达的消息/开方一律拒绝（见第 11 节 EX-IM-14 / EX-IM-15）。

**现状差异**：全新能力，现状无。

### FR-P1 医生开具处方

**需求描述**：医生在 `ONGOING` 会话内根据病情开具处方。处方要素：**药品（= 会话目标药品）、数量、用法用量（单次用量/每日次数/用法）、有效期（默认 7 天）**。**医生只能给本会话开处方**，且处方药品必须等于会话目标药品；开方成功后会话按 FR-C4 自动结束。

- 处方号：服务端生成 `RX + yyyyMMddHHmmss + 4位随机数`，唯一索引兜底。
- 处方归属：`prescription.sessionId`、`prescription.userId`、`prescription.doctorId`、`prescription.productId` 均在开方时落库快照。
- 用法用量为必填文本/数值：单次用量（如「0.25g」）、每日次数（如「每日 2 次」）、用法（如「口服」）、数量（如 1 盒）。任一缺失，医生端校验不通过，不允许开方。
- 开方成功后：处方 `ACTIVE`；会话自动结束（`PRESCRIPTION_ISSUED`）；推送系统消息。

**前置条件**：会话存在且状态 `ONGOING`；操作者为 `session.doctorId` 匹配的医生。

**主流程步骤**：
1. 医生在会话聊天页点击「开具处方」。
2. `order-service` 代理 `consult-service POST /api/prescriptions {sessionNo, doctorId, quantity, dosage, frequency, usage, validDays}`。
3. `consult-service` 校验：会话存在、状态 `ONGOING`；医生身份 = `session.doctorId`；处方药品 = `session.productId`（本会话药品）；用法用量非空且合法。
4. 生成处方号、写入处方（`ACTIVE`）、计算 `validUntil = 开方时间 + validDays`。
5. 会话置 `ENDED`（`PRESCRIPTION_ISSUED`），推送系统消息（含处方号与有效期）。

**后置条件**：处方 `ACTIVE` 且药品/用户/会话绑定正确；会话结束；用户端可见处方号与有效期。

**现状差异**：全新能力，现状无。

### FR-P2 凭处方下单

**需求描述**：用户凭有效处方购买 Rx 药品。下单时填写处方号 → `order-service` 调用 `consult-service` **原子消费**处方（校验 + 一次性置 `USED`）→ 通过后才走库存扣减与落单 → 支付。**一张处方只能消费一次**；下单数量**必须等于处方数量**。

- 入口：问诊聊天页「凭处方购买」/「我的处方」列表「凭此处方购买」/ Rx 详情页（存在 ACTIVE 处方时展示「凭已有处方购买」）。进入确认订单页时 `quantity` 锁定为处方数量、`prescriptionNo` 预填。
- 下单参数：`OrderForm` 新增可选字段 `prescriptionNo`；Rx 药品下单**必填**，OTC 药品下单**不要求**（OTC 可普通购买）。
- **消费顺序（防复用原子性）**：`consult-service POST /api/prescriptions/{no}/consume {productId, quantity, userId}` 内部执行**原子比对更新**：`UPDATE prescription SET status='USED', consumedOrderNo=?, usedAt=now WHERE no=? AND status='ACTIVE' AND validUntil>now AND productId=? AND quantity=? AND userId=?`，影响行数 = 1 才算消费成功；否则返回具体拒绝原因。
- 失败补偿：若处方消费成功后，后续「扣库存/落单」失败，调用 `consult-service POST /api/prescriptions/{no}/restore` 将处方**恢复为 `ACTIVE`**（best-effort，失败留日志人工对账），与 M1 库存补偿语义一致。

**前置条件**：用户身份合法；`product-service` / `consult-service` 可用。

**主流程步骤**：
1. 用户进入确认订单页（携带 `prescriptionNo`），`quantity` 锁定为处方数量。
2. `POST /order` 提交：`OrderService.createOrder(..., prescriptionNo)`：
   a. 拉取商品，若 `rxFlag=true`：
      - `prescriptionNo` 为空 → 拒绝「处方药需先在线问诊开具处方」；
      - 调用 `consult-service` 原子消费处方（见上）；消费失败按 EX-IM-2/3/4/5/6/7 返回具体提示；
   b. 调用商品服务**原子扣减库存**（沿用 M1）；
   c. 本地生成订单（状态 `CREATED`），`order.prescriptionNo` 记录处方号快照（Rx 订单必填）；
   d. 本地保存失败 → 补偿回补库存 + **恢复处方为 `ACTIVE`**。
3. 跳转订单详情，进入支付（沿用 M1 支付流程）。

**后置条件**：Rx 订单创建成功（`CREATED` + `prescriptionNo`）、处方状态 `USED`、库存已扣；同处方被拒请求未消费处方。

**现状差异**：M1 `OrderForm` 无 `prescriptionNo`，`Order.java` 无 `prescriptionNo` 字段，`OrderService.createOrder` 无处方校验逻辑——均需新增；OTC 商品行为不变。

### FR-P3 处方状态与有效期

**需求描述**：处方状态 `ACTIVE（有效）/ USED（已使用）/ EXPIRED（已过期）/ REVOKED（已撤销）`，单向流转；过期判定确定可测。

```
开具 ─▶ ACTIVE ──下单消费（原子）──▶ USED（终态）
         │
         ├── now > validUntil ──▶ EXPIRED（终态）
         └── 撤销（医生或用户，未使用）──▶ REVOKED（终态）
```

- **有效**：`ACTIVE`，处方开具后默认 7 天内有效。
- **已使用**：`USED`，被订单消费后进入，不可再消费、不可撤销。
- **已过期**：`EXPIRED`，`now > validUntil` 判定；在「消费/查询/状态展示」时**实时计算并落库**（懒判定），辅以每日定时扫描兜底。
- **已撤销**：`REVOKED`，处方未使用（`ACTIVE`）时，开方医生或所属用户可撤销（如开错方、放弃购买）；撤销后不可再消费。
- 「我的处方」列表展示该用户全部处方：处方号、药品、数量、用法用量、有效期、状态中文文案、来源会话；`ACTIVE` 处方提供「凭此处方购买」，`USED/EXPIRED/REVOKED` 仅展示。

**前置条件**：`consult-service` 可用；身份校验通过。

**主流程步骤**：
1. 用户访问「我的处方」→ 列表实时判定过期并落库后展示状态。
2. `ACTIVE` 处方 → 可点击「凭此处方购买」（进入 FR-P2）或「作废处方」（→ `REVOKED`）。
3. 医生在开方后的会话详情中可「撤销处方」（仅 `ACTIVE`，→ `REVOKED`）。

**后置条件**：状态机单向合法；过期处方不可下单；被撤销/已使用处方不可再消费。

**现状差异**：全新能力，现状无。

## 9. 用户流程（User Flow）

> 以下为「Rx 药品 → 问诊 → 开方 → 凭处方购药 → 支付」完整主路径的文字描述。

1. **浏览药品**：用户进入首页，浏览商品列表（含「药品」品类与 OTC/Rx 徽标）。点击 Rx 药品（如「阿莫西林胶囊」）进入详情页，看到「Rx · 处方药」与「需在线问诊开具处方后方可购买」。
2. **发起问诊**：点击「在线问诊购药」→ 系统创建（或复用）针对该药品的问诊会话 → 进入聊天页 `/consult/{sessionNo}`，状态「等待医生接入」。
3. **医生接入**：演示医生在「待接诊」列表看到会话并点击「接诊」→ 会话变为「进行中」，系统消息「医生已接入会话」。
4. **描述病情与回复**：用户发送文字描述病情（如「咳嗽三天，痰黄，有青霉素过敏史」）；医生实时文字回复（如「需确认无青霉素过敏，建议阿莫西林 0.5g 每日 3 次」）。双方消息实时可见、历史可查。
5. **医生开方**：医生点击「开具处方」，填写数量（如 1 盒）、单次用量（0.5g）、每日次数（3 次）、用法（口服）→ 提交成功 → 处方 `RX...` 生效，会话自动结束，系统消息展示处方号与有效期（默认 7 天）。
6. **凭处方购药**：用户在聊天页/「我的处方」点击「凭处方购买」→ 进入确认订单页（数量锁定 = 处方数量，处方号预填）→ 填写收货信息 → 提交订单。
7. **下单校验**：订单服务调用处方服务**原子消费**该处方（校验有效/未使用/未过期/药品匹配/数量一致）→ 通过 → 原子扣减库存 → 生成订单（记录处方号）。
8. **支付**：进入收银台，走 M1 既有支付流程（支付宝/微信/银行卡）→ 支付成功页。
9. **（可选）回看**：用户可在「我的问诊」查看历史会话，「我的处方」查看处方状态（有效/已使用/已过期/已撤销）。

> OTC 药品路径与 M1 一致：详情页「立即购买」→ 确认订单 → 提交 → 支付，无需问诊。

## 10. 非功能需求（NFR）

| 编号 | 分类 | 需求描述 | 验收要点 |
| --- | --- | --- | --- |
| NFR-1 | 实时性 | **消息端到端延迟**（发送→接收方展示）≤ 500ms（P95，本地演示环境）；WebSocket 长连接，心跳 15s/次、心跳超时 30s | 本地压测消息延迟 |
| NFR-2 | 并发 | 支持 ≥ 50 个并发在线问诊会话（演示量级）；多用户可同时各自发起问诊、医生可同时接入多个会话 | 并发建会话/发消息不报错 |
| NFR-3 | 并发 | **消息不乱序**：同一会话内 `seq` 单调递增，双端（用户/医生）同时发送时接收顺序与发送顺序一致；服务端按会话串行落库与转发 | 双端并发发送，接收顺序一致 |
| NFR-4 | 隔离 | **会话隔离**：用户只能查看/加入**自己**的会话与处方（`userId` 校验）；医生只能操作**自己接入**的会话（`doctorId` 校验）；浏览器无法通过篡改参数访问他人数据 | 跨会话访问被拒 |
| NFR-5 | 并发 | **处方一次性消费**：同一处方并发被两个订单消费时仅一个成功（原子比对更新）；其余被拒 | 并发下单只成一个 |
| NFR-6 | 可靠性 | **消息不丢**：消息**先落库成功再转发/确认**；断线 60s 缓冲期内重连按 seq 增量补拉，历史无缺失 | 断线重连后消息齐全 |
| NFR-7 | 可靠性 | 会话结束判定**不误判**：进行中有活动的会话不被断线/超时规则误结束；心跳不计入活动、医生输入刷新活动时间 | 活跃会话不被误结束 |
| NFR-8 | 一致性 | 状态机单向合法：会话 `WAITING→ONGOING→ENDED`、处方 `ACTIVE→USED/EXPIRED/REVOKED`，不可逆、不跨跳；`ENDED` 会话拒绝再发消息/再开方 | 非法流转全部被拒 |
| NFR-9 | 安全性 | **处方防伪造/防复用**：处方号由服务端生成；消费必须服务端原子校验（存在/ACTIVE/未过期/药品匹配/数量一致/归属正确），前端不可构造或绕过；Rx 无处方下单被服务端拒绝（不仅前端隐藏按钮） | 伪造/复用/绕过后端全被拒 |
| NFR-10 | 安全性 | **身份越权防护**：所有问诊/处方操作服务端校验 `userId`/`doctorId` 归属，非法访问返回「无权访问」 | 越权操作被拒 |
| NFR-11 | 可用性 | 任一服务异常不导致白屏/500：`consult-service` 不可用时问诊/下单给出明确提示且不产生脏数据；下单错误统一 `{"message":"..."}` | 断连 consult-service，页面不崩溃 |
| NFR-12 | 可维护性 | 服务间错误体统一 `{"message":"..."}`；枚举 JSON 保持 name（`WAITING/ONGOING/ENDED`、`ACTIVE/USED/EXPIRED/REVOKED`），中文文案走 DTO `statusLabel`（沿用 M1） | 前端/服务间解析一致 |

| EX-IM-22 ★ | 处方消费成功后扣库存/落单失败 | 补偿：回补库存 + **恢复处方为 `ACTIVE`**；恢复失败留日志人工对账，不产生「处方被占但无订单」的悬挂 |

### 11.2 问诊相关

| 编号 | 异常场景 | 期望行为 |
| --- | --- | --- |
| EX-IM-9 ★ | 问诊中用户关闭浏览器/断网 | 连接断开；**60s 内重连** → 会话继续、消息按 seq 补齐；**超 60s** → 会话自动结束（`DISCONNECT_TIMEOUT`） |
| EX-IM-10 ★ | 医生未接入（会话长时间 `WAITING`） | 会话**保持 `WAITING` 不自动结束**；页面提示「等待医生接入」；用户可主动结束 |
| EX-IM-11 ★ | 断线后重连 | 重连成功后历史消息（含离线期间他人消息）按 seq 补齐，**不丢、不乱序** |
| EX-IM-12 ★ | 断线超过时限（60s） | 会话自动结束（`DISCONNECT_TIMEOUT`），推送系统消息 |
| EX-IM-13 ★ | 空闲超时（`ONGOING` 连续 30min 无消息） | 会话自动结束（`IDLE_TIMEOUT`） |
| EX-IM-14 ★ | 会话结束与用户发消息同时发生 | 按会话串行化：先结束 → 后到的消息被拒「会话已结束」；先发消息 → 正常接收后再结束；**不出现半状态** |
| EX-IM-15 ★ | 会话结束与医生开方同时发生 | 同上，结束后的开方被拒「会话已结束，无法开方」 |
| EX-IM-16 ★ | 演示医生忙碌/离线 | 新会话停留在 `WAITING`，用户消息**持久化但暂未回复**，页面提示「医生暂离，正在等待接入」；**不**因医生离线自动结束会话（防误判） |
| EX-IM-17 ★ | 已结束会话再发消息 | 拒绝「会话已结束，无法发送消息」 |
| EX-IM-18 ★ | 已结束会话再开方 | 拒绝「会话已结束，无法开具处方」 |
| EX-IM-19 ★ | 用户访问他人会话/处方 | 拒绝「无权访问该会话/处方」 |
| EX-IM-20 ★ | 非法状态流转（如对 `ENDED` 会话「接诊」、对 `ONGOING` 重复开方） | 服务端状态机前置校验，非法流转一律拒绝并返回明确提示 |
| EX-IM-23 ★ | 对 OTC 药品发起问诊会话 | 拒绝「该药品为非处方药，无需问诊」 |
| EX-IM-24 ★ | 医生开方用法用量缺失/非法 | 校验不通过，拒绝开方并提示补全 |

### 11.3 并发与竞态

| 编号 | 异常场景 | 期望行为 |
| --- | --- | --- |
| EX-IM-25 ★ | 同一会话双端（用户/医生）同时发消息 | 服务端按会话串行分配 `seq`，双方收到的顺序一致，**不乱序** |
| EX-IM-26 ★ | 同一处方两个订单同时下单 | 仅一个消费成功（原子比对更新），另一个拒绝「处方已使用」；**处方复用率 = 0** |
| EX-IM-27 ★ | 空闲超时结束与用户发消息同时发生 | 按会话串行化，结果确定：先结束时消息被拒；先发消息时消息成功后再结束；不误判、不半状态 |
| EX-IM-28 ★ | 多用户同时发起多个问诊会话 | 全部创建成功且互不可见（隔离）；同一用户对同一药品并发建会话 → 只新建一个，另一请求复用/返回同一会话（去重） |

## 14. 附录：状态机、关键接口与集成点

### 14.1 会话状态机

```
创建 ─▶ WAITING（等待医生接入）
           │  医生接入
           ▼
         ONGOING（进行中）
           │  ① 用户/医生主动结束 ② 断线超 60s 未重连
           │  ③ ONGOING 空闲 30min 无消息 ④ 医生开方成功
           ▼
         ENDED（已结束，终态；只读，禁止再发消息/再开方）
```

- `endReason`：`USER_ENDED / DOCTOR_ENDED / DISCONNECT_TIMEOUT / IDLE_TIMEOUT / PRESCRIPTION_ISSUED`。
- `WAITING` 不因「医生未接入」自动结束；空闲超时仅从 `ONGOING` 开始计时。

### 14.2 处方状态机

```
开具 ─▶ ACTIVE（有效，默认有效期 7 天）
           ├── 下单原子消费 ──▶ USED（已使用，终态）
           ├── now > validUntil ──▶ EXPIRED（已过期，终态）
           └── 医生/用户撤销（未使用）──▶ REVOKED（已撤销，终态）
```
