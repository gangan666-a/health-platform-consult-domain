## 1. 项目背景

0802-3 已交付一版 Spring Boot 微服务商城，包含商品、订单、支付三个服务，可在浏览器完成「浏览商品 → 下单 → 模拟支付」闭环。本期（0802-4）的核心诉求是引入 **AI 智能导购**：让系统在用户下单后、尤其是支付完成后，基于用户刚购买的商品，主动推荐「同类商品」与「互补商品」，提升用户二次购买的可能性。

系统现状要点（摘自代码）：

- **四个微服务**：`product-service`（:8081，商品）、`order-service`（:8082，BFF，承载全部页面）、`payment-service`（:8083，模拟支付）、`recommend-service`（:8084，AI 智能导购，无数据库）。
- **数据**：MySQL 8.4，每服务独立 schema（`shopdb_product` / `shopdb_order` / `shopdb_payment`），JPA `ddl-auto=update` 自动建表。
- **推荐引擎**：`recommend-service` 调用 DeepSeek 大模型（`deepseek-v4-flash`，关闭思考、JSON 输出）；未配置 API Key 或调用失败时自动回退到「品类规则推荐」；推荐服务整体不可用时页面隐藏推荐区块、不影响订单与支付。
- **状态机**：订单状态 `CREATED（待支付）→ PAID（已支付）` 或 `CREATED → CANCELLED（已取消）`，不可逆。
- **金额**：全程 `BigDecimal`（12 位精度、2 位小数）。

## 2. 目标用户

| 用户类型 | 描述 | 主要诉求 |
| --- | --- | --- |
| **普通买家（核心用户）** | 在商城浏览、下单、支付的个人用户 | 快速找到商品、顺畅下单支付、支付后获得有价值的「还要买什么」的推荐 |
| **店铺运营（间接用户）** | 关心销售转化与客单价 | 通过推荐位带动二次购买、清库存、提升客单价 |
| **研发 / 测试（系统用户）** | 开发与质量保障人员 | 明确可测试的需求边界、异常行为、验收标准 |

> 说明：本系统为演示级商城，**不含用户账号体系与登录鉴权**（见 4. 非目标）。所有用户行为视为同一匿名买家。

---

## 3. 项目目标

1. **G1 · 完整交易闭环**：用户可在浏览器完成「浏览商品 → 选数量 → 填收货信息 → 下单 → 模拟支付（支付宝/微信/银行卡）→ 查看订单」全流程，且库存、状态、金额正确。
2. **G2 · AI 智能导购**：下单后在订单详情页展示「同类商品推荐」；支付成功后在支付成功页同时展示「同类商品推荐」与「互补商品推荐」，每条推荐附推荐理由。
3. **G3 · 推荐高可靠可用**：AI 不可用（无 Key / 超时 / 异常 / 推荐服务宕机）时，推荐功能降级为规则推荐或自动隐藏，**绝不阻断下单与支付**。
4. **G4 · 关键正确性保障**：并发下不超卖、支付/取消/回调具备幂等性、卡号脱敏存储、金额全程一致。

## 6. 名词与术语

| 术语 | 说明 |
| --- | --- |
| BFF | 面向页面的后端聚合层，本系统中为 `order-service`，浏览器唯一入口 :8082 |
| 同类推荐（similar） | 推荐与已购商品**同品类**的其他商品（升级款/竞品），以商品 `category` 字段为准 |
| 互补推荐（complement） | 推荐与已购商品**搭配**的其他商品（如买手机→推耳机），按品类互补权重或模型语义 |
| 订单状态 | `CREATED 待支付` / `PAID 已支付` / `CANCELLED 已取消`，单向流转 |
| 支付流水 | `payment-service` 中一笔支付尝试的记录，状态 `PROCESSING / SUCCESS / FAILED` |
| 原子扣减 | 单条 `UPDATE ... SET stock=stock-? WHERE id=? AND stock>=?`，影响行数为 0 即库存不足 |
| 三层校验 | AI 结果校验：① 必须在商品目录内 ② 不得是已购商品 ③ 去重；同类模式额外校验品类一致 |
| 降级 / 兜底 | 无 Key、模型异常、服务不可用时的替代方案：规则推荐或隐藏区块 |

## 7. 用户角色与权限

| 角色 | 可访问能力 | 权限边界 |
| --- | --- | --- |
| **匿名买家（唯一角色）** | 浏览商品、看详情、下单、支付（模拟）、取消、看订单、看推荐 | 无后台管理、无其他用户数据；**不可**重复支付、**不可**取消已支付订单、**不可**篡改金额 |
| 系统内部服务（订单→商品/支付/推荐） | 通过内部 REST 调用实现编排 | 商品扣减/回补库存、支付回调、推荐请求均为服务间调用，不暴露给浏览器直接操作（推荐 API、支付 API 仅服务内部使用，虽无鉴权，但前端不会直接调用） |
| 研发/测试 | 执行验收标准、回归 | 可模拟异常（停服务、去 Key、并发） |

> 权限约束具体落在「服务端最终校验」：页面校验仅为体验，**业务正确性由服务端判定**（如库存边界在商品服务原子扣减、重复支付在支付服务拒绝、非法取消在订单服务拒绝）。

## 8. 功能需求（Functional Requirements）

> 编号规则：FR-x 为功能编号；AC 编号见第 12 节（AC-FRx-y）。

### FR-1 商品浏览 / 详情

**需求描述**：用户可从首页（商品列表）浏览全部在售商品，并可进入单个商品详情页查看完整信息、选择购买数量。

- 列表页（`/` 或 `/products`）：展示全部商品，字段含名称、价格、库存、图片、品类；按 `id` 升序。
- 详情页（`/product/{id}`）：展示商品名称、描述、价格、库存、品类、图片，并支持选择数量（≥1）进入确认订单。
- 页面展示的库存为**提示信息**，最终库存边界以下单时商品服务的原子扣减为准。

**前置条件**：`product-service` 可用；数据库 `product` 表存在且已初始化（种子数据 31 个商品、15 个品类）。

**主流程步骤**：
1. 用户访问首页 `/`，`order-service` 代理请求 `product-service GET /api/products` 获取全量商品，渲染列表。
2. 用户点击某商品进入 `/product/{id}`，`order-service` 调用 `GET /api/products/{id}` 获取详情。
3. 用户输入数量（默认 1），点击「立即购买」跳转 `/order/confirm?productId=&quantity=`。

**后置条件**：详情页正确渲染；选择数量跳转到确认订单页，超出库存时提示「购买数量超过库存」。

**现状差异**：无。

---

### FR-2 下单（确认订单 + 提交订单）

**需求描述**：用户确认商品与数量、填写收货人/手机号/地址后提交订单；系统生成订单号、写入订单与明细快照，并扣减库存。

**前置条件**：商品存在、数量在 1~999 之间、库存充足；收货三项非空；`product-service` 可用。

**主流程步骤**：
1. 确认页（`GET /order/confirm`）校验：`quantity<1` 重置为 1；`quantity>stock` 抛「购买数量超过库存」。
2. 提交（`POST /order`）表单校验：`productId` 非空、`quantity` ∈ [1,999]、收货人/手机号/地址非空，任一不满足回填确认页并展示错误。
3. `OrderService.createOrder`：
   a. 再次校验 `quantity>0`；
   b. 拉取商品详情，若 `stock < quantity` 抛「库存不足」；
   c. 调用商品服务**原子扣减库存** `POST /api/products/{id}/stock/deduct?quantity=`（并发正确性唯一边界，失败抛「库存不足」）；
   d. 计算 `totalAmount = unitPrice × quantity`；
   e. 生成订单号 `SO + yyyyMMddHHmmss + 4位随机数`，写入 `order` 与 `order_item` 明细快照（含商品名/单价/数量/小计），状态 `CREATED`；
   f. 本地保存失败时，补偿调用商品服务回补库存（补偿失败则留给人工对账）。
4. 跳转 `/order/{orderNo}` 订单详情页。

**后置条件**：订单创建成功（状态 `CREATED`）、库存已扣减、订单详情页展示订单与明细快照；订单详情页下方展示「同类商品推荐」（见 FR-7）。

**现状差异**：无。

---

### FR-3 库存扣减 / 回补

**需求描述**：库存扣减必须**原子且防超卖**；取消订单时回补库存。页面库存只是提示，服务端原子扣减是最终边界。

**前置条件**：`product-service` 可用；商品存在；扣减/回补数量为正整数。

**主流程步骤**（扣减）：
1. 校验 `quantity>0`，否则抛「扣减数量必须大于 0」。
2. 确认商品存在（不存在抛「商品不存在」）。
3. 执行原子扣减 `UPDATE product SET stock=stock-? WHERE id=? AND stock>=?`。
4. 影响行数为 0 → 抛「库存不足，当前库存仅 X 件」；否则返回扣减后的商品。

**主流程步骤**（回补）：
1. 校验 `quantity>0`，否则抛「回补数量必须大于 0」。
2. 确认商品存在。
3. 执行 `UPDATE product SET stock=stock+?`，返回回补后的商品。

**后置条件**：库存与真实剩余一致；并发下不超卖（同时多个请求成功扣减的总量 ≤ 原库存）。

**现状差异**：无。

---

### FR-4 支付（三种支付方式 + 银行卡绑定）

**需求描述**：用户对待支付订单发起模拟支付，支持三种方式：**支付宝（扫码）**、**微信支付（扫码）**、**银行卡（先选银行并绑定卡号，再输入 6 位支付密码）**。支付成功后订单置为 `PAID`，支付流水置 `SUCCESS`；仅保存卡号**尾号 4 位**。

**前置条件**：订单存在且状态为 `CREATED`；`payment-service` 与 `order-service` 可用；银行卡支付需在前端完成卡号绑定（16~19 位）与 6 位密码输入。

**主流程步骤**：
1. 进入支付页 `GET /order/{orderNo}/pay`：
   - 订单 `PAID` → 直接重定向到支付成功页；
   - 订单 `CANCELLED` → 抛「订单已取消，无法支付」；
   - 否则渲染收银台，展示应付金额（以订单金额为准，前端不可修改）。
2. 选择支付方式：
   - 支付宝/微信：展示二维码（确定性伪随机生成的 SVG，同一订单同一码），点击「我已扫码完成支付」提交。
   - 银行卡：选择银行（工/建/招/农/中/交）→ 输入 16~19 位卡号 → 点击「绑定银行卡」（前端校验位数，绑定后展示 `**** **** **** 尾号`）→ 输入 6 位支付密码 → 点击「确认支付」提交。
3. `POST /order/{orderNo}/pay` 转发 `payment-service POST /api/payments`：
   a. 拉取订单，`PAID` → 抛「订单已支付，请勿重复支付」；`CANCELLED` → 抛「订单已取消，无法支付」；
   b. **防重复支付**：该订单已存在非 `FAILED` 的流水 → 抛「该订单已发起过支付，请勿重复操作」；
   c. 提取卡号尾号 4 位（仅数字、不足 4 位不保存）；
   d. 写流水 `PROCESSING`（金额=订单金额、支付方式、银行、尾号）；
   e. 回调 `order-service POST /api/orders/{orderNo}/confirm-payment` 将订单置 `PAID`；
   f. 回调成功 → 流水置 `SUCCESS`；回调失败 → 流水置 `FAILED` + 失败原因，并上抛异常。
4. 支付成功 → 携带 `paid=true` 重定向到 `/order/{orderNo}/pay/success`。

**后置条件**：订单 `PAID`、流水 `SUCCESS`、支付成功页展示订单 + 同类推荐 + 互补推荐（见 FR-7/FR-8）；数据库中无完整卡号。

**现状差异**：支付方式为空时前端默认「支付宝」提交（`ShopController` 兜底为支付宝）。

### FR-5 订单取消

**需求描述**：用户对**待支付**订单执行取消；取消后订单置 `CANCELLED`，并逐明细回补库存。

**前置条件**：订单存在且状态为 `CREATED`；`product-service` 可用（用于回补库存）。

**主流程步骤**：
1. 用户在订单详情页/订单列表点击「取消订单」。
2. `OrderService.cancelOrder`：
   a. 订单不存在 → 抛「订单不存在」；
   b. 状态 `PAID` → 抛「订单已支付，无法取消」；状态 `CANCELLED` → 抛「订单已取消」；
   c. 对每个明细调用 `POST /api/products/{id}/stock/restore?quantity=` 回补库存；
   d. 置 `CANCELLED` + `cancelledAt`。
3. 跳转订单列表，提示「订单已取消，库存已恢复」。

**后置条件**：订单 `CANCELLED`，库存恢复到取消前水平；该订单不可再支付、不可再取消。

**现状差异**：无。

### FR-6 订单列表

**需求描述**：展示全部订单（含待支付/已支付/已取消），按创建时间倒序；每单展示订单号、金额、状态中文文案、下单时间，并提供「继续支付 / 取消」入口（视状态而定）。

**前置条件**：`order-service` 可用。

**主流程步骤**：
1. 用户访问 `/orders`。
2. `OrderService.listOrders` 拉取全部订单并渲染（懒加载明细）。
3. 待支付订单可点击继续支付（跳转收银台）或取消；已支付/已取消订单无操作入口。

**后置条件**：列表正确展示；无订单时展示空状态。

**现状差异**：无。

### FR-7 同类商品推荐（similar）

**需求描述**：根据用户**已购商品**（本次订单明细快照），从**全量商品目录**中推荐同品类商品（升级款/竞品/同品类其他型号），并附推荐理由。展示位置：
- **订单详情页** `/order/{orderNo}`（下单后即可看到）；
- **支付成功页** `/order/{orderNo}/pay/success`（同类 + 互补同时展示）。

**前置条件**：订单存在；`order-service` 能获取已购明细与全量目录；`recommend-service` 可用或可降级。

**主流程步骤**：
1. 页面渲染时，`order-service` 组装 `RecommendRequest{type="similar", purchasedItems=订单明细快照, catalog=全量商品}`。
2. 调用 `recommend-service POST /api/recommendations`。
3. 推荐服务编排（`RecommendationService.recommend`）：
   a. 先尝试 AI 同类推荐；AI 不可用/失败返回空；
   b. 结果不足 `topN`（默认 4）时用规则同类推荐补足；再用互补/热销补足；
   c. 全程去重（`picked` 集合）。
4. 返回 `items[]`，每条含 `productId/productName/price/imageUrl/reason/source(ai|rule)`。
5. 页面用 `th:if` 判断空列表隐藏推荐区块。

**后置条件**：推荐结果**全部**满足「目录内、非已购、不重复」，同类模式下额外满足「与已购同品类」（AI 结果经三层校验 + 品类校验，规则结果按品类构造天然满足）；每条带推荐理由；条数 ≤ `topN`。

**现状差异**：无。

### FR-8 互补商品推荐（complement）

**需求描述**：支付成功页额外展示「✨ AI 智能导购 · 你可能还需要」区块，推荐与已购商品**互补/搭配**的商品（含同类升级），并附理由。

**前置条件**：订单已支付成功；已购明细与全量目录可获取；`recommend-service` 可用或可降级。

**主流程步骤**：
1. 支付成功页渲染时，`order-service` 组装 `RecommendRequest{type="complement", purchasedItems, catalog}`。
2. 与同类推荐**并行**调用（`CompletableFuture`），避免两个 DeepSeek 请求串行拖慢页面。
3. 推荐服务编排：AI 互补优先 → 不足 `topN` 用规则互补补足 → 全程去重。
4. 返回 `items[]`；页面按空列表隐藏区块。

**后置条件**：推荐结果满足「目录内、非已购、不重复」；条目 ≤ `topN`；带理由；与同类推荐结果独立计算、可重叠但各自去重。

**现状差异**：无。

### FR-9 推荐降级（AI → 规则 → 隐藏）

**需求描述**：推荐能力在多种异常下逐级降级，任何情况下**不阻断下单与支付**、不报错。降级链路：**DeepSeek AI → 规则推荐 → 隐藏区块**。

| 场景 | 降级行为 |
| --- | --- |
| 未配置 API Key | `AiRecommendationService` 直接返回空 → 全部走规则推荐（`source=rule`） |
| DeepSeek 调用异常/超时/返回非法 JSON/模型输出幻觉商品 | 内部捕获异常返回空（不抛）→ 规则补足；非法/幻觉条目被三层校验丢弃 |
| AI 结果不足 `topN` | 规则推荐补足剩余名额 |
| 推荐服务整体不可用 / 网络异常 | `RecommendClient` 吞异常返回空列表 → 页面隐藏推荐区块 |

**前置条件**：`order-service` 与 `recommend-service` 的容错边界（`RecommendClient`）生效；页面模板具备空列表隐藏逻辑。

**主流程步骤**：
1. `RecommendClient.call` 对任何异常记日志并返回空列表（**永不抛异常**）。
2. `recommend-service` 内：AI 失败返回空 → 规则补足；规则也不足则返回空列表。
3. 页面 `th:if` 依据空列表隐藏区块；`source` 字段决定角标文案（🤖 AI 推荐 / 同类优选 / ✨ 搭配推荐）。

**后置条件**：推荐服务不可用时，下单/支付/订单展示完全不受影响；推荐区块可用性 100%（可能为空/隐藏）。

**现状差异**：无。

## 9. 用户流程（User Flow）

> 以下为「浏览 → 支付成功 → 看推荐」完整主路径的文字描述。

1. **浏览**：用户访问 `http://localhost:8082`，进入商品列表页，浏览 31 个商品（名称/价格/库存/品类）。点击任一商品进入详情页。
2. **选数量**：在详情页选择购买数量（≥1），点击「立即购买」。
3. **确认订单**：系统校验数量 ≤ 库存后展示确认订单页：商品、单价、数量、总价（`单价 × 数量`），用户填写收货人、手机号、地址。
4. **提交订单**：用户点击提交，系统校验表单（数量 ∈ [1,999]、收货信息非空）→ 原子扣减库存 → 生成订单（`CREATED`）与明细快照 → 跳转订单详情页。
5. **看同类推荐**：订单详情页展示订单信息（待支付，可去支付/取消），下方展示「🔄 同类商品推荐」（此时同类推荐已可看到）。
6. **发起支付**：用户点击「去支付」进入收银台：
   - 支付宝/微信：扫二维码 → 点击「我已扫码完成支付」；
   - 银行卡：选银行 → 绑卡（16~19 位）→ 输入 6 位支付密码 → 确认支付。
7. **支付确认**：支付服务校验订单（待支付、无进行中流水）→ 记录流水（仅尾号 4 位）→ 回调订单服务置 `PAID` → 流水 `SUCCESS` → 重定向支付成功页。
8. **看推荐**：支付成功页展示订单与支付信息，并**并行**加载两块推荐：🔄 同类商品推荐 + ✨ AI 智能导购「你可能还需要」（互补）。任一块为空或推荐服务不可用则自动隐藏，不影响本页。
9. **（可选）回看**：用户可到「我的订单」查看历史订单，待支付订单可继续支付或取消；取消后库存回补。

## 10. 非功能需求（NFR）

| 编号 | 分类 | 需求描述 | 验收要点 |
| --- | --- | --- | --- |
| NFR-1 | 可用性 | 页面在任何服务异常下不出现白屏/500 崩溃；REST 错误统一返回 `{"message":"..."}`，页面错误统一渲染 `error.html` | 断连任一服务，其余页面仍可用 |
| NFR-2 | 容错 | **推荐服务不可用绝不影响下单/支付/订单展示**；推荐调用永不抛异常（`RecommendClient` 吞异常） | 停掉 recommend-service，下单与支付流程完全正常，推荐区块隐藏 |
| NFR-3 | 容错 | AI 无 Key / 失败时降级规则推荐，页面照常展示推荐（角标区分来源） | 去除 Key 后仍出推荐，`source=rule` |
| NFR-4 | 安全 | 银行卡号**全链路脱敏**：支付请求卡号仅走内部传输，数据库/订单/响应只存**尾号 4 位** | 查询订单、流水均无完整卡号 |
| NFR-5 | 安全 | 订单号唯一（唯一索引兜底）；金额全程 `BigDecimal`，不做浮点运算 | 订单号不重复；金额精确到分 |
| NFR-6 | 并发 | **库存防超卖**：以商品服务原子扣减（`WHERE stock>=?`）为唯一边界，页面校验仅是提示 | 并发下成功下单总数 ≤ 原库存 |
| NFR-7 | 幂等 | 支付确认回调幂等：订单已 `PAID` 时重复回调直接返回成功，不报错、不改状态 | 重复 `confirm-payment` 不抛异常 |
| NFR-8 | 幂等 | 防重复支付：同一订单已存在非 `FAILED` 流水时拒绝再次支付 | 重复发起支付被拒绝 |
| NFR-9 | 幂等 | 订单号生成确定性 + 随机段，极小概率冲突依赖唯一索引兜底（保存失败→回补库存） | 冲突时不产生脏数据 |
| NFR-10 | 性能 | 支付成功页含两次并行推荐，整体渲染 ≤ 3s（P95）；推荐服务内部超时 `12s` | 压测/超时用例 |
| NFR-11 | 一致性 | 状态机单向流转：`CREATED→PAID`、`CREATED→CANCELLED`，不可逆、不跨跳 | 非法流转全部被服务端拒绝 |
| NFR-12 | 可维护性 | 服务间错误体统一 `{"message":"..."}`；枚举 JSON 保持 name，中文文案走 `statusLabel` | 前端/服务间解析一致 |

## 11. 边界与异常场景（Anti-Happy-Path）

> 每条给出**期望行为**；对应可测试验收见第 12 节 AC。`★` 标注为测试必须重点覆盖的防 happy path 场景。

| 编号 | 异常场景 | 期望行为 |
| --- | --- | --- |
| EX-1 ★ | 库存不足（下单时库存 < 数量） | 下单失败，提示「库存不足，当前库存仅 X 件」，不扣减库存、不生成订单 |
| EX-2 ★ | 并发抢购导致库存临界 | 原子扣减保证超卖部分拒绝（影响行数 0 → 提示库存不足），成功单数 ≤ 库存 |
| EX-3 ★ | 购买数量为 0 / 负数 | 表单校验或服务端拦截，提示「购买数量必须大于 0」，不生成订单 |
| EX-4 ★ | 购买数量超上限（>999） | 表单校验失败，提示「单次最多购买 999 件」 |
| EX-5 ★ | 商品不存在（浏览/下单） | 提示「商品不存在」；下单不扣库存、不落订单 |
| EX-6 ★ | 商品价格异常（≤ 0，数据脏数据） | 应为异常数据治理项：下单时金额校验不通过即拒绝，避免产生负金额/零金额订单（现状无显式校验，需研发补强） |
| EX-7 ★ | 商品刚被下架/删除（提交时不存在） | 商品服务抛「商品不存在」，下单失败并提示重选 |
| EX-8 ★ | 重复支付回调（幂等） | 订单已 `PAID` 时再次回调 `confirm-payment` 直接返回成功，不抛错、不改动状态、不重复计流水 |
| EX-9 ★ | 已支付订单再次发起支付 | 支付服务拒绝：「订单已支付，请勿重复支付」；支付页 `PAID` 订单直接跳支付成功页 |
| EX-10 ★ | 已取消订单发起支付 | 支付服务拒绝：「订单已取消，无法支付」；支付页 `CANCELLED` 抛同样提示 |
| EX-11 ★ | 已存在进行中/成功流水时再次支付 | 支付服务拒绝：「该订单已发起过支付，请勿重复操作」（`FAILED` 流水允许重试） |
| EX-12 ★ | 已支付订单再次取消 | 取消被拒：「订单已支付，无法取消」，状态保持 `PAID`，库存**不**回补 |
| EX-13 ★ | 已取消订单再次取消 | 取消被拒：「订单已取消」，不重复回补库存（避免库存虚增） |
| EX-14 ★ | 非法状态流转（非法路径直达） | 服务端对每个状态变更做前置校验，非法流转一律拒绝并返回明确提示；状态机单向 |
| EX-15 ★ | 支付回调失败（确认订单失败） | 支付流水置 `FAILED` + 失败原因并上抛，不永久卡在 `PROCESSING`；用户可重试支付 |
| EX-16 ★ | 支付流水查询不存在 | 提示「支付记录不存在」 |
| EX-17 ★ | 支付金额与订单金额不符 | 服务端**不接收前端金额**，支付金额一律取订单金额，天然杜绝不符；若出现不一致属数据异常，以订单金额为准并告警 |
| EX-18 ★ | 重复下单（同一商品多次提交） | 每次提交生成独立订单（各自扣库存），语义为合法多次购买；不视为错误，但库存要逐次正确扣减 |
| EX-19 ★ | 本地保存订单失败 | 补偿回补库存（尽力而为）；补偿失败则记录待人工对账，不产生无订单的扣减遗留 |
| EX-20 ★ | 下单中途 `product-service` 不可用 | 下单失败并提示「商品服务不可用，请稍后重试」，不落订单 |
| EX-21 ★ | 支付中途 `payment-service` 不可用 | 前端提示「支付服务不可用，请稍后重试」，订单保持 `CREATED` 可重试 |
| EX-22 ★ | 推荐服务不可用 | `RecommendClient` 吞异常返回空列表；订单详情/支付成功页**正常渲染**，推荐区块隐藏；不影响下单与支付 |
| EX-23 ★ | DeepSeek 未配置 API Key | AI 返回空 → 规则推荐兜底，推荐照常展示，角标为规则来源 |
| EX-24 ★ | DeepSeek 调用超时/5xx/网络异常 | AI 内部捕获返回空（不抛）→ 规则补足；页面不报错 |
| EX-25 ★ | 模型返回非法 JSON / 带 Markdown 围栏 | 解析失败返回空 → 规则补足；围栏会被剥离后尝试解析 |
| EX-26 ★ | 模型返回**幻觉商品**（不在目录内） | 三层校验①目录内过滤 → 丢弃该条，不展示 |
| EX-27 ★ | 模型推荐**已购商品** | 三层校验②非已购过滤 → 丢弃该条 |
| EX-28 ★ | 模型返回**重复商品**（多条相同 id） | 三层校验③去重 + 编排层 `picked` 集合 → 仅保留首条 |
| EX-29 ★ | 模型推荐条数不足 `topN` | 规则推荐补足剩余名额，保证页面不空旷 |
| EX-30 ★ | 模型返回条数超出 `topN` | 截断至 `topN` |
| EX-31 ★ | 同类模式下模型推荐了**不同品类**商品 | 同类模式第 4 层品类校验过滤；规则同类按品类构造天然满足 |
| EX-32 ★ | 已购商品无 `category`（老数据） | 按商品名关键词推断品类；推断不出则不强制同类，交由规则兜底 |
| EX-33 ★ | 银行卡号非 16~19 位 / 含非法字符 | 前端拦截：「银行卡号应为 16~19 位数字」；服务端不足 4 位则不入库尾号 |
| EX-34 ★ | 银行卡支付密码非 6 位 | 前端拦截：「请输入 6 位支付密码」 |
| EX-35 ★ | 银行卡支付未绑定卡号直接提交 | 前端流程约束（未绑定不提交）；服务端对缺失卡号不保存尾号，不构成安全风险 |
| EX-36 ★ | 订单号生成碰撞（同秒 ≥10000 单） | 唯一索引兜底：保存失败 → 回补库存 + 提示重试，不产生脏订单 |
| EX-37 | 页面库存展示与实际不一致 | 属可接受（提示性），最终以下单原子扣减为准；不允许出现超卖下单成功 |
| EX-38 | 数据库/服务中途重启（演示级分布式事务） | 存在「已扣库存未落订单/未回补」的崩溃窗口，属已知演示限制（见 NG-4），人工对账兜底 |

## 14. 附录：状态机与关键接口

### 14.1 订单状态机

```
               取消（仅CREATED，回补库存）
 CREATED ───────────────────────────────▶ CANCELLED
    │
    │  支付成功回调（幂等，仅CREATED）
    └──────────────────────────────────▶ PAID
   （PAID / CANCELLED 均为终态，不可再变）
```

### 14.2 关键内部接口（服务间 REST）

| 服务 | 接口 | 说明 |
| --- | --- | --- |
| product | `GET /api/products` | 商品列表 |
| product | `GET /api/products/{id}` | 商品详情 |
| product | `POST /api/products/{id}/stock/deduct?quantity=` | 原子扣库存 |
| product | `POST /api/products/{id}/stock/restore?quantity=` | 回补库存 |
| order | `GET /api/orders/{orderNo}` | 订单详情（支付服务校验用） |
| order | `POST /api/orders/{orderNo}/confirm-payment` | 支付确认回调（幂等） |
| payment | `POST /api/payments` | 发起支付 |
| payment | `GET /api/payments/{orderNo}` | 查询流水 |
| recommend | `POST /api/recommendations` | AI 智能导购（type=similar/complement） |
