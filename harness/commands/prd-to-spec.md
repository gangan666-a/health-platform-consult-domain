## 2. 研发补全清单（Spec 独有，PRD 没有但代码需要）

> 纪律：每一项都必须**从 PRD 或既有方案（`docs/02-solution-design.md`）可推导**。推导不出的 = 发明需求，记入 OPEN，回产品确认。**不得发明 PRD 没要求的业务行为。**

| 补全项 | 内容 | 推导来源 |
| --- | --- | --- |
| **API 契约** | 方法 / 路径 / 请求 / 响应 JSON schema / 错误码 / 幂等性 | PRD §14.2 接口表 + 方案 §3 API 契约 |
| **数据模型** | 表 / 列 / 类型 / 约束 / 索引 / 快照语义 | 方案 §4 数据库设计 |
| **状态机** | 当前 Feature 涉及的合法流转表 | PRD §14.1 + 方案 §6 |
| **边界与校验规则** | 数值边界、格式校验、并发边界、默认值（fail-closed） | PRD FR/EX/NFR + 方案 §8 |
| **事务与补偿边界** | 跨服务动作的补偿/幂等/失败兜底 | 方案 §7/§8（先扣后补、回调幂等） |
| **测试映射** | 单测 / 接口测 / 集成测 → 覆盖哪些 Spec 项 | 方案 §10 测试策略 |
| **改造定位** | 新增/修改/删除哪些 `类.方法`，位置(file:line/插入点)，变更前后对比，必须保持的不变量 | **静态调用链 `docs/trace/01` §6 + 动态 trace `docs/trace/03` + `gitnexus context <symbol>` / grep 实测**；三者缺证据 = 落点存疑，回代码核证，不得凭印象写 |
| **规则引用** | 本 Feature 触及模块的必守 `T-x/C-x`（中间件/通信/一致性/校验/幂等） | `harness/references/tech-rules.md` + `code-rules.md`；**不许自造模式**，缺规则先扩展 rules |
| **模块约束** | §13 引用对应 `harness/agents/<module>.md` 的 DO/DON'T 与不变量 | 按 §3.5 落点定位到哪个模块，就读哪个 agents 文件 |

## 3. 歧义探测器（fail-closed，Stage 1 用）

命中以下任一 → 该项标 **OPEN**，转化器**不猜测**，回产品澄清：

- **模糊措辞**：`可能 / 也许 / 视情况 / 待定 / 优化 / 尽量 / 若干 / 合理 / 友好提示 / 视业务而定`
- **不可量化目标**：无数字、无边界、无时间、无判定标准（如「体验更好」）
- **未定义术语**：出现但术语表无定义
- **前后矛盾**：同一行为两处描述不一致
- **多选一未定**：「A 或 B」未说明取舍规则

**OPEN 记录格式**（汇入 Spec §12 待澄清项）：
```
| 编号 | 来源位置 | 问题 | 澄清需求 |
| OPEN-1 | 01-PRD.md FR-2 主流程 | 回补失败的兜底只写了「留给人工对账」 | 需产品确认是否本期要做落库对账 |
```

## 4. 追溯与自包含规范

- **追溯引用**：每条 Spec 项带 PRD 引用 `(ref: FR-2 / AC-FR2-3 / EX-19 / NFR-6)`。研发补全项标 `(ref: SD-02 §5.1)`（方案设计）或 `(derived)`（纯推导，须附推导理由）。
- **自包含**：每条 Spec 项给出「在哪个文件、哪个章节、怎么验证」。禁止「based on findings, fix it」式把责任推回 PRD 或上一阶段。
- **反向可查**：从 PRD 任一 FR/AC/EX 能定位到对应 Spec 章节（用追溯矩阵 `docs/spec/COVERAGE.md` 保证）。
